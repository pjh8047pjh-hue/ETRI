## §1. 연산 정의 (확정)

### 1.1 전체 블록 중 이번 범위

`torchvision` MobileNetV2 `features[8]` = InvertedResidual, t=6, 64→64, 14×14, stride 1, residual 있음.

```
in[64][14][14]  ← mobilenetv2_result_layer07.bin
  ├─ (1) Expand PW 1×1   64→384   ← ★ 이번 주 범위
  ├─ (2) BN + ReLU6                ← ★ 이번 주 범위
  ├─ (3) Depthwise 3×3 s1 p1  384→384
  ├─ (4) BN + ReLU6
  ├─ (5) Project PW 1×1  384→64
  ├─ (6) BN (linear)
  └─ (7) residual add:  out += in
out[64][14][14] ← mobilenetv2_result_layer08.bin
```

**주의**: `mobilenetv2_result_layer08.bin`은 (7)까지 끝난 **블록 최종 출력**이다.
이번 주 검증 대상은 (2)까지의 중간 결과 `[384][14][14]`이며, 이 골든은 **직접 생성해야 한다** (§9.1).

### 1.2 수식

```
                63
acc[oc][h][w] =  Σ  in[ic][h][w] · W[oc][ic]                    (1×1 conv, 위치별 독립)
                ic=0

y = γ[oc]·(acc − μ[oc]) / √(σ²[oc]+ε) + β[oc]                    (BN, inference)
out[oc][h][w] = clamp(y, 0, 6)                                    (ReLU6)
```

### 1.3 BN fold (확정: fold 방식 채택)

```
s[oc] = γ[oc] / √(σ²[oc] + ε)          ε = 1e-5
b[oc] = β[oc] − μ[oc]·s[oc]
W'[oc][ic] = W[oc][ic] · s[oc]
```
→ 하드웨어는 아래 한 줄만 수행:
```
out[oc][h][w] = clamp( Σ in[ic][h][w]·W'[oc][ic] + b[oc], 0, 6 )
```

**fold 정당성 (실측)**: fold 경로 vs BN-후처리 경로, float 최대 차이 **2.384e-07** → float 반올림 수준. 무손실.
**하드웨어 이득**: `sqrt`, 나눗셈, 채널별 곱셈기 384개분이 전부 사라진다. BN은 **ROM 2개(W', b)** 로 흡수됨.

### 1.4 파라미터 출처

[../mobilenetv2_parameters.h](../mobilenetv2_parameters.h) (동일 파일이 `06_25/06_26/` 트리에도 중복 존재, 내용 동일)

| 배열명 | 크기 | 헤더 라인 | 용도 |
|---|---|---|---|
| `features_8_conv_0_0_weight` | 24576 | L379–380 | W (oc-major: `[oc*64+ic]`) |
| `features_8_conv_0_1_weight` | 384 | L382–383 | γ (gamma) |
| `features_8_conv_0_1_bias` | 384 | L385–386 | β (beta) |
| `features_8_conv_0_1_running_mean` | 384 | L388–389 | μ |
| `features_8_conv_0_1_running_var` | 384 | L391–392 | σ² |

**두 가지 함정**
1. **헤더는 소수점 6자리 `%f`로 덤프되어 있다.** 즉 파라미터 자체가 이미 ~1e-6로 양자화된 상태.
   16-bit 고정소수점(LSB 3.05e-5)에는 영향 없지만, "float 골든과 bit-exact"를 기대하면 안 되는 이유다.
2. **`running_mean`이 전 채널 0**이다 (6자리에서 `0.000000`/`-0.000000`). 따라서 실질적으로 `b[oc] = β[oc]`.
   fold 코드는 일반형으로 쓰되, 이 사실은 디버깅 시 sanity check로 쓸 수 있다.

## §2. 고정소수점 포맷 (확정)

### 2.1 실측 동적 범위 (layer07 실제 데이터 + 실제 weight)

| 신호 | 개수 | 실측 범위 | 필요 정수비트(부호 제외) |
|---|---|---|---|
| 입력 `in` | 12,544 | −1.7711 ~ +1.9837 | 1 |
| `W'` (fold된 weight) | 24,576 | −0.1297 ~ +0.1419 | −2 |
| `b` (fold된 bias) | 384 | −0.2453 ~ +0.4497 | −1 |
| conv 누산 결과 (BN 전) | 75,264 | −1.3159 ~ +1.2340 | 1 |
| 최종 출력 (BN+ReLU6 후) | 75,264 | 0 ~ **0.7608** | 0 |

### 2.2 확정 포맷

| 신호 | 총 비트 | 부호 | 정수부 | 소수부 | Q 포맷 | 스케일 | 표현 범위 | LSB |
|---|---|---|---|---|---|---|---|---|
| `IFM` 입력 | **16** | 1 | **3** | **12** | **Q3.12** | 2⁻¹² | −8 ~ +7.99976 | 2.4414e−4 |
| `W'` weight | **16** | 1 | **0** | **15** | **Q0.15** | 2⁻¹⁵ | −1 ~ +0.99997 | 3.0518e−5 |
| 곱 결과 | 32 (유효 31) | 1 | 3 | 27 | Q3.27 | 2⁻²⁷ | ±8 | 7.451e−9 |
| `b` bias | **32** | 1 | **4** | **27** | **Q4.27** | 2⁻²⁷ | −16 ~ +16 | 7.451e−9 |
| 누산기 `acc` | **32** 이상 | 1 | 4 | 27 | Q4.27 | 2⁻²⁷ | −16 ~ +16 | 7.451e−9 |
| `OFM` 출력 | **16** | 1 | **3** | **12** | **Q3.12** | 2⁻¹² | 0 ~ 6.0 (클램프) | 2.4414e−4 |

- 표기 규칙: `Q<정수부>.<소수부>`, **부호 비트는 별도**. 즉 `총 비트 = 1 + 정수부 + 소수부`.
- 곱 결과의 정수부가 3인 이유: `Q3.12 × Q0.15` → 정수부 `3+0=3`, 소수부 `12+15=27`. 16×16 곱이 32비트
  컨테이너에 담기지만 부호 비트가 하나 중복되어 **유효 31비트**다.
- bias/누산기의 정수부가 4인 이유: 32비트 컨테이너에서 소수부 27을 쓰면 `32−1−27 = 4`가 남는다.
  곱보다 정수부가 1비트 넓어 **누산 헤드룸 역할**을 한다 (실측 필요 비트는 28, §2.4).

**정수 ↔ 실수 변환**: `실수 = 정수 / 2^F`, `정수 = round(실수 × 2^F)` (포화 적용)

### 2.3 연산 순서와 스케일 정합 (★ 여기서 틀리면 전부 틀림)

```
① acc ← b_q[oc]                          // Q4.27, 32bit.  초기값 = bias
② for ic in 0..63:
      acc ← acc + ifm_q · w_q             // Q3.12 × Q0.15 = Q3.27  → 스케일(2^-27) 자동 일치
③ y ← (acc + 2^14) >>> 15                // Q4.27 → Q3.12, round-half-up, 산술 시프트
④ if (y < 0)      y ← 0                  // ReLU6 하한
   if (y > 24576) y ← 24576              // ReLU6 상한 = 6.0 × 2^12 = 0x6000
⑤ OFM ← y[15:0]
```

- **shift량 = 15** 은 `(F_in + F_w) − F_out = (12+15) − 12` 에서 나온다. 상수다.
- **bias를 Q3.12로 양자화해서 ③ 이후에 더하면 안 된다.** 정밀도를 버리게 된다.
  Q4.27로 ①에 주입하는 것이 핵심.
- **③은 반올림을 쓸 것.** 단순 절삭(`>>>15`)은 최대 1 LSB의 *편향된* 오차를 만든다.
  구현: `acc + 16384` 후 산술 우측 시프트 15.

### 2.4 누산기 폭

| 기준 | 값 |
|---|---|
| 이론적 최악 (`64 × 32767 × 32768`) | 6.87e10 → **37 bit** |
| **실측 최대** (Fi=12, Fw=15) | **28 bit** |
| 권장 | **32 bit** (실측 대비 4비트 여유) — DSP48 P 레지스터를 쓰면 48비트가 공짜 |

실측 28비트는 이 이미지 한 장 기준이다. 32비트는 실측 대비 16배 여유이므로 안전.
DSP48E1의 P 레지스터에 직접 누산하면 48비트라 고민 자체가 사라진다.

### 2.5 정확도 근거 (fixed-point 시뮬 vs float, 출력 75,264개 전체)

| 입력 | weight | 출력 | max abs err | 출력 LSB | PSNR | 누산기 실측 |
|---|---|---|---|---|---|---|
| **Q3.12** | **Q0.15** | **Q3.12** | **2.54e−4** | 2.44e−4 | **66.8 dB** | 28 bit |
| Q3.12 | Q0.14 | Q3.12 | 3.65e−4 | 2.44e−4 | 65.1 dB | 27 bit |
| Q3.12 | Q0.16 | Q3.12 | 2.00e−4 | 2.44e−4 | 67.4 dB | 29 bit |
| Q3.13 | Q0.16 | Q1.14 | 1.01e−4 | 6.10e−5 | 76.9 dB | 30 bit |
| Q3.12 | Q0.13 | Q1.14 | 6.92e−4 | 6.10e−5 | 62.6 dB | 26 bit |

→ 권장안의 오차 2.54e−4 = **출력 LSB의 1.04배**. 이미 양자화 한계이므로 비트를 더 늘려도 의미 없다.

**대안 (원한다면)**: 출력을 Q1.14로 하면 77 dB까지 간다(해상도 4배). 단 ReLU6의 6.0을 표현할 수 없어
(Q1.14 최대 1.99994) 클램프 상한을 포맷 최대값으로 대체해야 하고, 다음 layer와 포맷이 달라진다.
**포맷 통일 · 다음 단계 재사용성을 이유로 Q3.12를 권장한다.**

## §3. 데이터 파일 포맷 · `.coe` 변환 규칙 (확정)

### 3.1 `.bin` 포맷

| 항목 | 값 |
|---|---|
| 자료형 | IEEE-754 **float32, little-endian** |
| 헤더 | **없음** (순수 raw) |
| 차원 순서 | **CHW** (채널 → 행 → 열), 완전 연속 |
| 선형 인덱스 | `idx = c*196 + h*14 + w` (196 = 14×14) |
| `layer07.bin` 크기 | 50,176 B = 12,544 float = 64×14×14 ✓ |
| pointwise 골든 크기 | 301,056 B = 75,264 float = 384×14×14 |

**행 단위 연속성이 핵심**: `idx = c*196 + h*14 + w` 이므로 **한 행(14개)이 파일에서 연속**이다.
이것이 §5 후보 A(행 병렬)에서 전치가 전혀 필요 없는 이유다.

### 3.2 `.bin` → `.coe` 변환 규칙

```
1. float32 하나를 읽는다                          f
2. q = round(f × 2^F)          F: IFM=12, W'=15, b=27
3. 포화: q = clamp(q, −2^(N−1), 2^(N−1)−1)        N: IFM=16, W'=16, b=32
4. 2의 보수 N비트 → 16진수 (N/4 자리, zero-pad)
5. 워드 패킹(선택한 width에 따라): LSB에 가까운 쪽이 낮은 인덱스
```

**패킹 방향 규칙 (확정)**: width가 `16·P`인 워드에서 lane `j`는 `word[16*j +: 16]`.
즉 **lane 0이 최하위 16비트**. `.coe` 생성기와 RTL 슬라이싱이 같은 규칙을 써야 한다.

```systemverilog
logic [16*P-1:0]    ifm_dout;
logic signed [15:0] px [P];
always_comb for (int j = 0; j < P; j++) px[j] = ifm_dout[16*j +: 16];
```

### 3.3 `.coe` 파일 문법

```
memory_initialization_radix=16;
memory_initialization_vector=
ef30,
fd27,
fc6c,
...
fb79;
```
- 주소 0부터 순서대로 한 워드씩. 마지막만 `;`
- 32비트 폭이면 8자리(`01405d53`), 224비트 폭이면 56자리
- BMG **Fill Remaining Memory Locations = 0** 으로 두면 벡터가 depth보다 짧아도 됨

## §4. 메모리 논리 사양 (확정)

물리 width/depth는 §5의 데이터플로 선택에 따라 달라진다. **논리적으로 담아야 하는 내용은 고정이다.**

| # | 이름 | 담는 것 | 원소 수 | 원소 폭 | 총 비트 | 접근 방향 |
|---|---|---|---|---|---|---|
| 1 | `IFM` | `in[ic][h][w]` Q3.12 | 12,544 | 16 | 200,704 | compute가 **read only** |
| 2 | `WROM` | `W'[oc][ic]` Q0.15 | 24,576 | 16 | 393,216 | **read only** (상수) |
| 3 | `BROM` | `b[oc]` Q4.27 | 384 | 32 | 12,288 | **read only** (상수) |
| 4 | `OFM` | `out[oc][h][w]` Q3.12 | 75,264 | 16 | 1,204,224 | compute가 **write only** |

### 4.1 논리 인덱스 → 원본 파일 인덱스 (확정)

| 메모리 | 논리 인덱스 | 원본 선형 인덱스 |
|---|---|---|
| `IFM` | `in[ic][h][w]` | `layer07.bin[ic*196 + h*14 + w]` |
| `WROM` | `W'[oc][ic]` | `features_8_conv_0_0_weight[oc*64 + ic] × s[oc]` |
| `BROM` | `b[oc]` | `β[oc] − μ[oc]·s[oc]` |
| `OFM` | `out[oc][h][w]` | `golden_pw.bin[oc*196 + h*14 + w]` |

**OFM은 CHW로 저장할 것 (확정 권장)**: 골든 `.bin`과 주소가 1:1로 대응되어 바이너리 비교가 그대로 되고,
다음 주 depthwise 3×3의 행 접근에도 유리하다.

### 4.2 IP 종류 선택 기준 (확정)

**"쓰는 쪽과 읽는 쪽이 다른가"로 결정한다.**

| 메모리 | IP | 이유 |
|---|---|---|
| `WROM`, `BROM` | **Single Port ROM** (BMG) | 상수. write 포트가 아예 필요 없다. True Dual Port는 낭비 |
| `IFM` | **Simple Dual Port RAM** (BMG) | A포트 = 로더 write / B포트 = datapath read. 이번 주는 `.coe` 프리로드만 써도 되지만, SDP로 만들어 두면 다음 주 AXI 연결 때 그대로 재사용 |
| `OFM` | **Simple Dual Port RAM** (BMG) | A포트 = datapath write / B포트 = 덤퍼(또는 다음 단) read |
| `BROM` 대안 | **Distributed Memory Generator ROM** | 384×32 = 12 Kb뿐. LUTRAM으로 뽑으면 BRAM 0개, 지연 1사이클 |

**True Dual Port는 양쪽 포트가 모두 write할 때만 쓴다. 여기엔 해당 없음.**

### 4.3 BMG 설정 체크리스트 (확정)

| 옵션 | 값 | 이유 |
|---|---|---|
| Common Clock | **체크** | 단일 클럭 도메인 |
| Primitives Output Register | **켜기** | Fmax 확보. addr→dout **2 사이클**이 되며, §6에서 이를 전제로 파이프라인을 짠다 |
| Operating Mode (OFM write 포트) | **No Change** | 그 포트로 읽지 않으므로 전력 최소 |
| Byte Write Enable | 끄기 | 필요 없음 |
| Load Init File | `WROM`/`BROM`은 `.coe` 필수, `IFM`은 선택 | |
| Fill Remaining Memory Locations | 0 | |

**시뮬 반복 속도 팁**: 개발 중에는 `xpm_memory_sdpram` 또는 SV 배열 + `$readmemh`가 훨씬 빠르다.
**메모리를 파라미터화된 wrapper 모듈로 감싸두면** 시뮬은 inferred RAM / 합성은 BMG로 스위치할 수 있다.
Vivado 합성·타이밍이 목표이므로 최종 빌드는 BMG로 돌려서 자원·Fmax를 확인한다.

## §5. 데이터플로 후보 — read/write 스케줄 (★ 선택 지점)

공통 사실: 출력 1개당 64 MAC. 총 MAC = 384 × 196 × 64 = **4,816,896**.
따라서 `사이클 ≈ 4,816,896 / (병렬 MAC 수)`.

핵심 질문은 하나다: **"한 사이클에 동시에 곱할 64개 중 몇 개를, 어느 축으로 잘라서 가져올 것인가?"**
1×1 conv는 공간 위치끼리 완전히 독립이므로 자를 축이 두 개 있다.

### 후보 A — 행(공간) 병렬 · output-stationary  ← 권장

한 채널의 **한 행 P픽셀**을 동시에 읽고, weight **스칼라 1개**를 P lane에 broadcast.

```
for oc in 0..383:                     // 출력 채널
  for h in 0..13:                     // 행
    acc[0..P-1] ← b[oc]               // 누산기 P개 초기화 (Q4.27)
    for ic in 0..63:                  // ← 내부 루프 (64 사이클)
      ifm_word = IFM[ic*14 + h]       // P픽셀 동시
      w        = WROM[oc*64 + ic]     // 스칼라 1개
      for j in 0..P-1:  acc[j] += ifm_word[j] · w      // 병렬, lane 간 통신 없음
    for j in 0..P-1:  OFM[oc*196 + h*14 + j] ← relu6(round_shift(acc[j]))
```

**사이클별 read/write (P=14, 한 (oc,h) 구간)**

| 사이클 | `IFM` read addr | `WROM` read addr | `BROM` read | `OFM` write |
|---|---|---|---|---|
| −1 | — | — | `addr = oc` | — |
| 0 | `ic=0 → 0*14+h` | `oc*64 + 0` | — | — |
| 1 | `ic=1 → 1*14+h` | `oc*64 + 1` | — | — |
| … | `addr += 14` | `addr += 1` | — | — |
| 63 | `ic=63 → 63*14+h` | `oc*64 + 63` | — | — |
| 64~67 | — (drain) | — | — | — |
| 68~81 | — | — | — | `oc*196+h*14+j`, j=0..13 순차 |

**주소 생성에 곱셈기가 필요 없다** — 이게 후보 A의 숨은 장점이다:
- `IFM addr`: 행 시작값에서 **매 사이클 +14** (누산 레지스터)
- `WROM addr`: **매 사이클 +1**
- `OFM addr`: **매 사이클 +1**
- 행이 끝나면 `IFM addr ← h+1`, `WROM addr ← oc*64` (oc 증가 시 +64 누산)

**장점**
- `.bin`이 CHW라서 한 행 14개가 이미 연속 → **전치 불필요**, `.coe` 생성기가 거의 공짜
- weight가 broadcast 스칼라 → **`WROM`이 16비트로 유지**됨 (넓히지 않아도 됨 = BRAM 절약)
- lane 간 합산이 없음 → **adder tree 불필요**, 각 lane이 독립 누산 = DSP48 P 레지스터 그 자체
- OFM write가 MAC 64사이클 뒤에 P개만 발생 → **OFM을 16비트 단일 포트로** 처리 가능

**단점**
- `P`가 14를 나눠야 자연스럽다 (P ∈ {1, 2, 7, 14}). P=8 같은 값은 행 경계가 어긋난다
- 누산기 레지스터 P개 필요

**P 선택표**

| P | `IFM` width | `IFM` depth | MAC 사이클 | @100 MHz | DSP48 | 누산기 |
|---|---|---|---|---|---|---|
| 1 | 16 | 12,544 | 4,816,896 | 48 ms | 1 | 1 |
| 2 | 32 | 6,272 | 2,408,448 | 24 ms | 2 | 2 |
| 7 | 112 | 1,792 | 688,128 | 6.9 ms | 7 | 7 |
| **14** (한 행) | **224** | **896** | **344,064** | **3.4 ms** | **14** | **14** |

**일반 `P`에 대한 주소식** (한 행이 `14/P` 워드로 쪼개짐, 워드그룹 `g = 0..14/P−1`):

```
IFM depth = 12,544 / P
IFM addr  = ic*(196/P) + h*(14/P) + g
사이클     = 4,816,896 / P          (= 384 × 14 × (14/P) × 64)
```

| P | IFM addr 식 | g 범위 |
|---|---|---|
| 14 | `ic*14 + h` | 0 (한 행 = 1 워드) |
| 7 | `ic*28 + h*2 + g` | 0..1 |
| 2 | `ic*98 + h*7 + g` | 0..6 |
| 1 | `ic*196 + h*14 + w` | 0..13 |

P=14에서만 `g` 루프가 사라져 `ic*14 + h`로 단순화된다 — 주소 생성이 가장 깔끔해지는 이유다.
P<14이면 루프가 `oc → h → g → ic` 4중이 되고, `w_addr`는 매 `g`마다 `w_base`로 되돌려야 한다.

### 후보 B — 채널 병렬

한 픽셀의 **입력 채널 N개**를 동시에 읽고, weight도 N개 읽어 **adder tree로 합산**.

```
for oc in 0..383:
  for p in 0..195:                    // 공간 위치
    acc ← b[oc]
    for k in 0..(64/N - 1):
      ifm_word = IFM[p*(64/N) + k]    // 채널 N개
      w_word   = WROM[oc*(64/N) + k]  // weight N개
      acc += Σ_{n} ifm_word[n]·w_word[n]        // N입력 adder tree
    OFM[oc*196 + p] ← relu6(round_shift(acc))
```

| N | `IFM` width/depth | `WROM` width/depth | 사이클 | @100 MHz |
|---|---|---|---|---|
| 4 | 64 / 3,136 | 64 / 6,144 | 1,204,224 | 12 ms |
| 8 | 128 / 1,568 | 128 / 3,072 | 602,112 | 6.0 ms |
| 16 | 256 / 784 | 256 / 1,536 | 301,056 | 3.0 ms |

**장점**: 누산기 1개. OFM write가 위치당 1회로 자연스러움. N이 2의 거듭제곱이라 주소 계산이 시프트로 끝남.
**단점**
- `.bin`이 CHW인데 채널 연속(HWC)이 필요 → **IFM을 전치해야 함** (`.coe` 생성기에서 처리)
- **`WROM`도 N배로 넓어짐** → 같은 24,576워드인데 BRAM 사용량이 늘어남
- **N입력 adder tree** 가 크리티컬 패스에 들어옴 (N=8이면 3단) → 파이프라인 단을 더 넣어야 Fmax 유지

### 비교 요약

| 항목 | 후보 A (행 병렬) | 후보 B (채널 병렬) |
|---|---|---|
| IFM 전치 | 불필요 ✓ | 필요 |
| WROM 폭 | 16비트 유지 ✓ | N×16으로 확대 |
| 합산 구조 | 독립 누산기 (adder tree 없음) ✓ | N입력 adder tree |
| 누산기 수 | P개 | 1개 ✓ |
| 주소 생성 | 증분(+14/+1), 곱셈기 없음 ✓ | 시프트 ✓ |
| 크리티컬 패스 | 짧음 ✓ | adder tree 만큼 김 |
| 병렬도 자유도 | 14의 약수 | 2의 거듭제곱 ✓ |

→ **후보 A, P=14를 권장한다.** 전치 불필요 + WROM 절약 + adder tree 없음이 합쳐져 이 문제에 가장 잘 맞는다.
다만 "adder tree를 직접 설계해 보는 것"이 학습 목표라면 후보 B도 충분히 합리적인 선택이다.

## §6. 파이프라인 · 타이밍 규격 (확정)

**여기가 실제 구현에서 가장 많이 틀리는 지점이다.** BMG의 output register를 켜면 `addr → dout`이
**2 사이클**이므로, 주소 발행 시점과 누산 시점이 어긋난다.

### 6.1 파이프라인 단

| 단 | 동작 | 비고 |
|---|---|---|
| S0 | 주소 생성 (`addr_ifm`, `addr_w` 출력) | 카운터/증분 레지스터 |
| S1 | BRAM 내부 latch | BMG 내부 |
| S2 | `dout` 유효 (`ifm_dout`, `w_dout`) | output register 출력 |
| S3 | 곱셈 `px[j] × w` | DSP48 M 레지스터 |
| S4 | 누산 `acc[j] += product` | DSP48 P 레지스터 |

**`IFM`과 `WROM`의 지연이 동일하므로 오퍼랜드 정렬은 자동**이다. 별도 지연 레지스터를 넣지 말 것.
필요한 것은 `valid`를 같은 단수만큼 shift register로 끌고 가서 `acc`의 enable을 제어하는 것뿐이다.

`acc` **초기화는 `LOAD_B` 단계에서 레지스터 로드로 끝낸다** (§7). DSP48을 직접 인스턴스화한다면
C 포트에 `b_q`를 넣고 첫 곱에서 `P ← C + M`, 이후 `P ← P + M`이 되도록 `OPMODE`를 제어하는 방식도
동등하며 사이클 하나를 절약한다. 어느 쪽이든 **초기화가 정확히 한 번만** 일어나는지 확인할 것.

### 6.2 사이클 상세 (한 (oc,h) 구간, P=14)

```
cyc  addr발행   dout유효   곱셈      누산
 0   ic=0        -          -        acc ← b[oc]   (bias 프리로드)
 1   ic=1        -          -        -
 2   ic=2       ic=0        -        -
 3   ic=3       ic=1       ic=0      -
 4   ic=4       ic=2       ic=1      += ic=0
 …
63   ic=63      ic=61      ic=60     += ic=59
64    -         ic=62      ic=61     += ic=60
65    -         ic=63      ic=62     += ic=61
66    -          -         ic=63     += ic=62
67    -          -          -        += ic=63      ← acc 확정
```

- **발행 64 + drain 4 = 68 사이클/행** (단순 구현)
- 총 사이클 = 384 × 14 × 68 = **365,568** (@100 MHz = 3.66 ms)
- **최적화**: 다음 행의 주소를 drain 구간에 겹쳐 발행하면 행당 64사이클로 줄어든다
  (→ 344,064 사이클). 단 누산기를 2세트로 두거나 경계 처리가 필요하다. **1차 구현에서는 68사이클로 두고,
  동작 확인 후 최적화할 것.**

### 6.3 후처리 단

`acc` 확정 후 shift + 라운딩 + ReLU6 클램프 + OFM write:

```
stage P0:  r = acc[j] + 32'sd16384          // 라운딩 상수
stage P1:  t = r >>> 15                     // 산술 우측 시프트 (Q4.27 → Q3.12)
stage P2:  y = (t < 0)      ? 16'sd0
             : (t > 24576)  ? 16'sd24576
             : t[15:0];
stage P3:  OFM.wea=1, OFM.addra=ofm_addr, OFM.dina=y
```

- **P개 lane을 병렬 처리할 필요 없다.** MAC 구간이 64사이클인데 출력은 14개뿐이므로,
  후처리 로직 **1세트를 14사이클에 걸쳐 재사용**하면 자원이 절약되고 OFM도 단일 포트로 충분하다.
- 라운딩과 클램프를 **별도 사이클로 분리**하면 크리티컬 패스가 짧아진다 (Vivado 타이밍 목표에 유리).

### 6.4 타이밍 목표

| 항목 | 목표 |
|---|---|
| 클럭 | 100 MHz (여유 확보 후 상향 검토) |
| 예상 크리티컬 패스 | 32비트 누산 덧셈, 또는 라운딩+클램프 경로 |
| 대책 | 누산은 DSP48 P 레지스터에 맡기고, 라운딩/클램프는 §6.3처럼 단 분리 |

## §7. FSM 상태별 신호 표 (참조 설계, 후보 A / P=14 기준)

| 상태 | `ifm_en` / `ifm_addr` | `w_en` / `w_addr` | `b_en`/`b_addr` | `acc` 동작 | `ofm_we` / `ofm_addr` / `ofm_din` | 전이 조건 → 다음 상태 |
|---|---|---|---|---|---|---|
| `IDLE` | 0 / – | 0 / – | 0 / – | hold | 0 / – / – | `start` → `LOAD_B` |
| `LOAD_B` | 0 / – | 0 / – | **1** / `oc` | `acc[j] ← b_q[oc]` (전 lane 동시, 레지스터 로드) | 0 | 1 cyc → `MAC` |
| `MAC` | **1** / `ic_cnt*14+h` (매 cyc **+14**) | **1** / `oc*64+ic_cnt` (매 cyc **+1**) | 0 | `valid_d2`일 때만 `acc[j] += px[j]*w` (초기화는 하지 않음) | 0 | `ic_cnt==63` → `DRAIN` |
| `DRAIN` | 0 / – | 0 / – | 0 | 남은 4단 누산 계속 | 0 | 4 cyc → `POST` |
| `POST` | 0 | 0 | 0 | hold | **1** / `oc*196+h*14+j_cnt` (매 cyc **+1**) / `relu6(rshift(acc[j_cnt]))` | `j_cnt==13` → `NEXT` |
| `NEXT` | 0 | 0 | 0 | clear | 0 | `h<13` → `h++`, `LOAD_B`<br>`h==13 && oc<383` → `oc++`, `h←0`, `LOAD_B`<br>`h==13 && oc==383` → `DONE` |
| `DONE` | 0 | 0 | 0 | – | 0 | `done=1`, `IDLE` |

**카운터 사양**

| 카운터 | 폭 | 범위 | 갱신 |
|---|---|---|---|
| `oc_cnt` | 9 | 0..383 | 행 14개 완료마다 +1 |
| `h_cnt` | 4 | 0..13 | 행 완료마다 +1 |
| `ic_cnt` | 6 | 0..63 | `MAC` 상태에서 매 사이클 +1 |
| `j_cnt` | 4 | 0..13 | `POST` 상태에서 매 사이클 +1 |
| `ifm_addr` | 10 | 0..895 | `MAC`에서 **+14**, 행 시작 시 `← h_cnt` |
| `w_addr` | 15 | 0..24575 | `MAC`에서 **+1**, 행 시작 시 `← w_base`. `w_base`는 oc 증가 시 **+64** |
| `ofm_addr` | 17 | 0..75263 | `POST`에서 **+1**. **리셋 불필요** ↓ |

**`ofm_addr`는 단순 선형 카운터다.** 출력 순서가 `oc → h → w`이고 OFM 주소가 `oc*196+h*14+w`이므로
전체 실행에 걸쳐 0부터 75,263까지 **한 방향으로만 증가**한다. 즉 `POST`에서 `+1`만 하면 되고
행/채널 경계에서 재계산할 필요가 없다.

곱셈기는 어디에도 필요 없다: `ifm_addr`은 +14, `w_base`는 +64, `ofm_addr`은 +1 — 전부 증분 누산이다.

### 9.1 골든 재생성 — 먼저 해야 할 일

기존 `JH_pointwise_output.bin`은 소스보다 타임스탬프가 앞서므로(15:35 vs 16:54) 이전 버전 산출물이며

### 9.2 2단 검증 전략 (★ 중요)

RTL을 float 골든에 직접 비교하면 안 된다. **양자화 오차와 RTL 버그가 섞여서 구분이 안 된다.**

```
Step 1:  C float 골든  ←→  C fixed-point 모델
         판정: max abs err ≤ 2.6e-4 (= 출력 LSB 1.04배), PSNR ≥ 66 dB
         목적: 포맷 선택이 타당한지 확인 (이미 검증 완료, §2.5)

Step 2:  C fixed-point 모델  ←→  RTL 시뮬레이션
         판정: 75,264개 전부 bit-exact (100%)
         목적: RTL 버그만 잡는다.  ← 여기서 1비트라도 틀리면 RTL 버그다
```

Step 2가 bit-exact여야 하는 이유: C 모델과 RTL이 **같은 정수 연산**(같은 라운딩, 같은 shift, 같은 클램프)을
수행하므로 결과가 완전히 같아야 정상이다. §2.3의 연산 순서를 C 모델과 RTL이 **글자 그대로 동일하게** 구현할 것.

## §10. 설계 결정 체크리스트 (직접 정할 항목)
